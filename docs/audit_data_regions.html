Constats

Ce qui ne fonctionne pas dans l'organisation actuelle

StructureBrut, dérivé, docs et datasets : tout au même endroit

  • Les sorties de pipeline vivent dans les livraisons, sous trois générations d'arborescences incompatibles (results/MNT|RVT ; indices/ + detections/ ; MNT/ + RVT/ nus) — aucun script ne localise les produits sans cas particulier par livraison.
  • De la vérité terrain est stockée dans des dossiers de sortie : la digitalisation Rambouillet est dupliquée à l'identique (40/40 fichiers, plus un PDF de 256 Mo en double) dont une copie dans l'output ; la GT/ de Fenétrange vit dans un run de détection. Première édition d'une copie = plus de version canonique.
  • 19 projets detections_validation.qgs (tailles toutes différentes) : du travail humain de validation stocké dans la zone « régénérable ». Toute purge naïve des outputs les détruirait — règle d'exfiltration obligatoire.
  • Haye_MNT_INDICES (~16 Gio de dérivés RVT) vit dans la livraison brute, hors output_pipeline_* : la dichotomie simple brut/dérivé ne le couvre pas.
  • Aucun .laz/.las sur tout l'arbre : le « brut » est déjà du dérivé (MNT). À assumer explicitement dans l'architecture (le nuage de points source vit ailleurs — IGN).
  • 33 Gio de datasets train/val/test sur le Drive alors que Roboflow est la source de vérité : snapshots non versionnés, sans lien vers la version Roboflow (data6 ? 40e ?).

NommageLe rangement géographique est faux et les noms ne portent pas le sens

  • Régions erronées (hypothèses fondées sur les préfixes de départements des dossiers, à confirmer) : la « bataille de la Marne » (préfixe 77 = Seine-et-Marne) est sous Hauts-de-France ; les « Vosges saônoises » (70 = Haute-Saône) sous Grand-Est ; « Rhône-Alpes » n'existe plus depuis 2016. Le niveau région n'est validé contre aucun référentiel.
  • Contradiction blois/aude non résolue : « data_aude » = prénom (projet SOLiDAR Blois/Chambord, 41) selon le contenu, mais le metadata.json de l'output blois pointe zone_aude_ign.shp et D:/data_aude/MNT (département 11 ?). À trancher avec le livreur avant tout renommage.
  • Accents et espaces dans toutes les racines (Île-de-France, Centre-Val de Loire), casse aléatoire (data_Verdun vs data_vosges), préfixe data_ récursif jusqu'à trois niveaux (data_Loire_Atlantique\data_Yann_Lejeune\data\).
  • Noms sans sémantique : d1…d8 (Verdun), patates.shp (Rambouillet), Download.zip (15,8 Go !), fichier .zip (espace avant l'extension — l'unique livraison de Bretagne).
  • La sémantique d'entité change de porteur selon la livraison : dans le nom de fichier (Haye_lidar_chaussee), dans la géométrie (digit_lignes2/points/poly, trois orthographes du même concept en Île-de-France), ou dans les attributs — impossible d'industrialiser la classification sans traitement au cas par cas.
  • Entités fusionnées (fossébutte), suffixes parasites (fours_a_chaux_dou), versions côte à côte sans contrat (parcellaire_v1/_v2 ; 02_MNT_v1 vs 02_MNT_v2 dont les fichiers internes s'appellent 05_MNT_*), collision de casse Fours_a_chaux.gpkg / fours_a_chaux.shp (même clé normalisée, formats mixtes).
  • Pollution : 222 desktop.ini, verrous ArcGIS .sr.lock livrés (preuve qu'un poste de travail édite en direct sur le partage), .lyr ArcGIS porteur de la périodisation (illisible nativement dans QGIS), doubles extensions .pdf.pdf, entité HTML fossilisée dans un nom de PDF, doublons de sync *_detections (1).jpg, ~4,9 Gio de duplication interne aux outputs.
Cible

Architecture proposée : RAW / TRANSFORMED par zone

Conforme au schéma que vous avez fixé : chaque zone livrée par un archéologue sépare le brut immuable du transformé, ce dernier en deux étages — vecteurs nettoyés (taxonomie normalisée), puis payload exact d'upload Roboflow. L'ancien arbre n'est jamais modifié : il est gelé, la v2 naît propre à côté.

data_regions_v2/
  <region>/<dept>_<site>[_<annee>]/          # ex. grand_est/55_verdun/ · noms 100 % normalize()
    manifest.yaml                            # OBLIGATOIRE — la carte d'identité de la zone
    raw/                                     # livraison intacte, zip d'origine inclus — écriture unique, plus jamais touché
    transformed/
      vecteurs/                              # couches nettoyées : GPKG, EPSG:2154, entités = taxonomy/entities.yaml
      roboflow/                              # payload d'upload : tuiles + _annotations.coco.json + upload_manifest.yaml
    docs/                                    # rapports, thèses, autorisations DRAC (licence d'usage !)

hors data_regions_v2 :
  sorties de pipeline → local (D:) ; sur le Drive, seulement les livrables légers d'un run
  (shapefiles de détections, configs, metadata, logs, .qgs de validation) — jamais les
  milliers de jpg/tif intermédiaires. Layout unique : indices/ + detections/<model>/.
  exports d'entraînement → Roboflow (source de vérité) ; tout export local est un cache
  daté portant sa référence de version Roboflow.

Le manifest.yaml (généré à ~80 % par l'outillage)

zone_id: 55_verdun                      # = nom du dossier = tag Roboflow
region: grand_est                       # validé contre le référentiel des 13 régions
departement: 55
source: { contact: "Nom <email>", organisme: "", date_reception: 2026-07-16, licence: "" }
donnees:
  crs: EPSG:2154
  contenu:
    - { path: raw/…, type: mnt, resolution_m: 0.5 }
    - { path: transformed/vecteurs/…, type: labels, entites: [charbonniere, four] }
integrite: { nb_fichiers: 0, taille_octets: 0, checksums: checksums.sha256 }
roboflow:
  projet: <projet-par-modele>
  tags: [55_verdun, grand_est]          # zone + région, charset [a-z0-9_] conforme
  upload_manifest: transformed/roboflow/upload_manifest.yaml   # image_id ↔ filename ↔ tags

La mécanique Roboflow (vérifiée dans la doc officielle)

  • Upload par image — project.single_upload(image_path=…, annotation_path=coco, tag_names=["55_verdun","grand_est"], batch_name="55_verdun_2026-07", split=…). L'upload de dossier (workspace.upload_dataset) ne supporte pas les tags : notre outillage bouclera par image. Batch = trace d'upload ; tags = le vrai véhicule.
  • Correction en masse a posteriori — lister par l'API Search (query: "tag:x", fields: [id, filename, tags]), corriger par lots (updates[].addTags/removeTags) ou remplacer intégralement (operation: "set"). La session de rattrapage des tags existants est entièrement scriptable.
  • Entraîner par sous-ensemble de zones — génération de version avec preprocessing: {"filter-tags": …} (Require/Exclude) : un projet par modèle + tags suffit, pas de duplication de projets.
  • Piège central : l'export COCO ne préserve pas les tags. Le upload_manifest.yaml local (image_id ↔ filename ↔ tags), alimenté à chaque upload et correction, est la seule voie fiable de réconciliation — c'est une pièce obligatoire du volet transformed/roboflow/.
